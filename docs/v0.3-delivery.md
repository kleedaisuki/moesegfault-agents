# v0.3 delivery and acceptance ledger

## Intended outcome

This release adds Responses alongside the existing Chat Completions API, without
arbitrary historical or workspace forks. It also adds an owner-scoped Space with
managed files and immutable workspace versions. The implementation must remain a
single durable execution engine, not a second harness hidden behind new routes.

The release boundary is working public SDK, dashboard and CLI journeys, not only
serializable response fixtures. Staging is authorized for implementation and
acceptance. Production must only receive the identical accepted artifacts through
the existing Actions promotion gate. Existing v0.1/v0.2 tags, data, pins, credentials
and consumer contracts must remain valid.

## Coordination and review boundaries

Architecture and protocol decisions are recorded in
[the Responses/Space design](responses-spaces-v0.3.md); tests and independent
coverage are recorded in [the verification matrix](v0.3-verification.md).
Implementation owners coordinate shared Rust modules and migration numbers before
editing. Root alone commits, pushes, dispatches delivery and promotes artifacts.

Heavy Rust/Wasm/container checks run in Actions. Local work is restricted to
focused inexpensive probes and genuine client/browser journeys. Failed remote
jobs are investigated from their exact logs/artifacts, not repeatedly restarted
without an explanatory change. Any partial deployment is reconciled at the same
source before switching release candidates.

cancellation transport, and admission hardening discovered by independent review.
No failed-run artifact is eligible for deployment, and no v0.3 staging or
production deployment has occurred at this point. All requirement rows above
remain pending until their appropriate exact-source runtime gates pass.

## Functional baseline accepted in CI, deployment still pending

[CI 40118214256](https://github.com/kleedaisuki/moesegfault-agents/actions/runs/40118214256)
completed successfully for exact source
`588baafc66d73afd9290bfe65d5d6d2dc66f84f9`. All six normal jobs succeeded;
the optional artifact-diagnostic job was correctly skipped. The Worker job passed
215 library tests and all 39 actual-Wasm/SDK/transport checks, including an
isolated process crash with persistent-store recovery and no provider replay.
Native daemon import corrections, the CLI and the new dashboard also passed their
respective gates. This is the functional CI baseline, not real-provider or staging
acceptance of v0.3.

The intermediate build `bcdc3f0` exposed two real runtime defects: rejected fresh
requests leaked live-session admission, and returning local tool outputs could
leave them queued and incorrectly start an extra Chat run. The accepted baseline
corrects both without increasing quotas or hiding extra provider calls. Separate
fixture corrections preserve compaction/history oracles, primary failures and
legitimate uncertain provider receipts.

The `performance-v3` artifact records the production pager on the deterministic
128-tool-round workload. For one initial display, thirty unchanged polls and one
two-message append, JSON bodies fell from 19,018,414 to 118,551 bytes (4 KiB tool
outputs) and from 140,309,166 to 241,584 bytes (32 KiB outputs). Complete source
reconstruction passed. Request count rose from 32 to 34. These are measured native
serialization/pager results, excluding headers, compression, CPU and latency;
they are not an observed production traffic forecast.

The same successful run retained the exact tested container as `container-image`
alongside Worker and dashboard artifacts. Deployment verifies archive and loaded
image identity instead of rebuilding the container. Diagnostic-mode CI cannot
qualify for promotion: all normal jobs, workflow identity, source identity and
artifacts remain mandatory.

Before deployment, the next candidate must also pass the remaining protocol
boundary corrections, post-baseline text framing and conditional/range transfer
optimization, and the extended real binary-attachment/pin journey. No v0.3
environment has been deployed yet. The full requirement matrix remains open
until exact-source staging, native user journeys and release promotion complete.
