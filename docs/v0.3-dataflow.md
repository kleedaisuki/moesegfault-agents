# v0.3 data-flow optimization

## Workload and baseline

The dominant avoidable client transfer is repeated source-history retrieval, not
the model token stream itself. The [existing history measurement](session-history.md)
recorded 4,455,014 JSON bytes for 128 synthetic tool rounds with 32 KiB outputs.
The previous dashboard fetched that complete source journal on each status poll.
Compaction does not shrink this journal: it must preserve the original user data.

The v0.3 baseline remains the unchanged `GET /v1/sessions/{id}` representation.
It returns full history to existing consumers. Optimization is additive: a new
client can request a small metadata view and explicit source-message pages.
This does not change history ownership, infer a compacted transcript or hide
old messages from existing API clients.

## New read model

`GET /v1/sessions/{id}/view` returns current metadata without the immutable pin or
source history. The response carries an ETag computed over this small view, not
over all source bytes. Authorized callers send `If-None-Match`; an unchanged view
returns 304 with no body. Authentication and ownership checks still precede the
conditional result. Responses remain private; no cross-user cache is introduced.

The view must include every publicly observable status field so assistant/tool
completion, cancellation, archive/checkpoint state and local-tool handoff can
invalidate it without requiring another user append. Hashing `input_revision`
alone would incorrectly treat such changes as unchanged. Live token deltas do
not rewrite session status merely to advance a polling validator.

`GET /v1/sessions/{id}/messages` returns:

```json
{
  "object": "list",
  "data": [{"sequence": 78, "message": {"role": "user", "content": "..."}}],
  "start": 78,
  "end": 128,
  "high_water": 128,
  "before_cursor": "opaque",
  "after_cursor": "opaque",
  "has_older": true,
  "has_newer": false
}
```

The example abbreviates `data`: `start` is inclusive, `end` exclusive. Sequence
numbers identify the unchanged append-only source entries, not compacted prompt
positions. No cursor means the newest 50 entries. `before=<before_cursor>` loads
older entries, while `after=<after_cursor>` retrieves new appends; both return
ascending source order. `limit` is 1–100. Duplicate/conflicting parameters, foreign
session cursors and future positions fail rather than silently skipping content.

Pages have a 256 KiB soft entry budget as well as the entry-count limit. One whole
entry is always permitted even if oversized; otherwise a valid large tool result
could make pagination stall forever. Page envelope bytes are additional to that
soft entry budget. A counting writer measures candidates without allocating
copies of tool output. Page entries borrow original messages, preserving every
tool ID, reasoning continuation and provider extension field.

The dashboard initially reads the view plus a recent page. It fetches append
pages only when the metadata's `message_count` advances; an explicit older-history
control prepends earlier pages. It keeps sequence identity rather than matching
streamed optimistic text by content. A cursor remains valid when later source
entries append or when active prompt compaction occurs.

## Reproducible byte comparison

The production pager's library test
`session_views::tests::v3_dataflow_workload_preserves_history_with_bounded_repeat_transfer`
constructs actual provider `Message` and `ToolCall` values. It models 128 complete
tool rounds with deterministic 4 KiB and 32 KiB output cases. Each case compares:

1. One initial history render.
2. Thirty unchanged polls.
3. One observation of two newly appended messages.

The baseline makes 32 full-history reads. The optimized client makes 34 requests:
two initial resources, thirty conditional metadata reads, then one changed view
and one append page. Extra request headers/authentication work are an explicit
trade-off; unchanged requests have zero body bytes, not zero server cost.

The test serializes actual old/new bodies, uses the production pager and ETag
helpers, and reconstructs the entire final source from forward pages to assert
value equality. It rejects a body reduction smaller than 99% for this polling
workload. This is a deterministic regression target, not a live traffic forecast.

Run in the existing cached Worker CI build, without a separate compiler job:

```sh
cargo test --locked -p agents-worker --lib
# Or the focused test, after normal dependencies have already compiled:
cargo test --locked -p agents-worker --lib v3_dataflow_workload -- --nocapture
```

The machine-readable receipt is `.cache/perf/v3/dataflow.json`. It contains counts
and no source content, credentials or user IDs. Exact final-source CI results and
actual Worker/browser acceptance must be added before declaring the optimization
accepted. JSON body savings exclude HTTP headers, TLS framing, compression,
Worker/DO CPU, storage rehydration and client layout; they do not establish latency
or memory improvements. The two synthetic output sizes are not customer-derived
distributions.

After the same source is deployed to staging, use an already accepted idle/closed
test session for the read-only HTTP probe:

```sh
# Supply MAGENTS_TEST_API_KEY and MAGENTS_PERF_SESSION_ID through the environment.
node scripts/perf/v3-dataflow.mjs
node --test scripts/perf/v3-dataflow.test.mjs
```

The probe defaults to the staging hostname and refuses production. It samples one
full-history body, the new view/recent page and ten actual conditional reads, then
reconstructs older pages and checks original message/sequence equality. The old
repeated-body total is calculated from the stable baseline sample, not obtained
by repeatedly transferring megabytes solely to demonstrate waste. An unexpected
state change fails the comparison. Each response has a 16 MiB probe memory budget;
larger histories need a deliberately chosen separate setup, not an unbounded
local allocation. Output `.cache/perf/v3/deployed-read.json` records the actual
serving build and aggregate body counts, but never message content, file paths,
session identity or keys. It does not make inference, tool or mutation requests.

## Streaming hot-path review

Responses introduces many typed events. A per-token callback must not clone the
entire session, journal or accumulated event list. Extract only small run identity
and scalar metadata from a short borrow. Durable replay events must be appendable
without repeatedly rewriting a growing history. These are separate server-side
costs from HTTP polling and require dedicated event-count/write measurements;
the history body benchmark does not prove them optimized.

### Coalescing policy experiment, before a production change

`node scripts/perf/v3-response-framing.mjs` compares deterministic provider
fragment schedules with immediate emission, a callback-only 1 KiB/50 ms policy,
and the same policy with a deadline timer. Node v26.10.0 on 2026-10-25 produced:

| Synthetic workload | Immediate delta frames / SSE body bytes | Timer delta frames / SSE body bytes | Timer maximum added fragment delay |
| --- | --- | --- | --- |
| 2,048 four-byte fragments, 2 ms apart | 2,048 / 545,706 | 83 / 29,845 | 50 ms |
| 512 eight-byte fragments, 20 ms apart | 512 / 138,130 | 206 / 57,958 | 50 ms |
| 512 mixed Unicode fragments, 10 ms apart | 512 / 135,826 | 104 / 28,930 | 50 ms |
| Three fragments at 0, 1 and 3,000 ms | 3 / 796 | 3 / 796 | 49 ms |

Every policy preserves the exact text and emits the first nonempty fragment
immediately. The callback-only policy delays the second quiet-gap fragment by
**2,999 ms**; checking elapsed time only when another provider fragment arrives
does not enforce a 50 ms delivery bound. The timer policy avoids that regression
without sacrificing the large burst framing reduction. Sparse traffic naturally
has little framing to save and should retain prompt visibility instead.

This is a policy simulation, not a production optimization receipt: it uses a
fixed Responses-like delta envelope and constant 24-character padding to isolate
frame count, not the running encoder's random padding or durable event cost.
Lifecycle, function arguments/results, item boundaries and terminal events must
remain ordered flush barriers. A production implementation requires actual
compiled-Worker/SDK tests for quiet gaps, completion flush, recovery sequence
numbers and slow observers; it must not claim these simulated savings as measured
deployment results. The receipt is `.cache/perf/v3/framing-policy.json`; two
focused Node tests validate text preservation and expose the callback-only gap.

## Sources

- [RFC 9110 conditional GET and entity tags](https://www.rfc-editor.org/rfc/rfc9110.html#name-if-none-match):
  GET validators use weak comparison and 304, not an application error or empty
  successful JSON object.
- [TanStack infinite queries](https://tanstack.com/query/latest/docs/framework/react/guides/infinite-queries):
  preserve page parameters and explicit pagination state rather than replacing
  a partial history with an unrelated full-query cache value.
- [Prior project source-history analysis](session-history.md): measured workload,
  compatibility boundaries and bounded DO journal rehydration already established
  before this release.
