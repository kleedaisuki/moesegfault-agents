# v0.3 release scope audit

Snapshot: 2026-10-27, integration `1726a72`, with explicit later in-flight owner
updates below. This is a release-readiness audit, not a claim that every current
OpenAI product is implemented or that v0.3 is live in production. The user requires
the full stable Responses scope recorded in [the contract inventory](full-responses-contract.md)
and [delivery decisions](full-responses-decisions.md); the initial linear-only
exclusions are superseded. Realtime, separate Agents/beta APIs and unrelated
standalone media endpoints are not silently added to that scope.

## Result

**Do not mark the objective complete or publish v0.3 yet.** The main missing work
is now concrete integration/real-runtime closure and release delivery, not an
absent Responses router. The currently running staging Worker is `02d483b`,
normal CI `40369812194`, deployment `40445875291`, with accepted daemon `3539c1c`
and dashboard `1b7f2cd`. Its feature selector is
`web_search,file_search,code_interpreter`; Image is disabled pending its repair.
This mixed-source deployment must retain the actual component identities.

The `v0.2.0` tag has no `response_routes.rs`, Space or full Responses dispatcher.
Production's existing Chat and management contracts must remain intact. A Cargo
version of `0.3.0`, candidate documentation, an enabled flag or a successful
compilation is not a production release receipt. Only tags `v0.1.0` and `v0.2.0`
exist at this audit snapshot.

## Material new issues, not old regressions to replay

1. **Image evidence and recovery:** the original response body was not retained
   and generic handling erased HTTP/codec details. The provider screenshot proves
   success and charge, but only a truncated generation ID. Do not invent the full
   ID or label it a provider failure. The root's new receiver retains encrypted
   raw bytes before parsing, distinguishes request/generation IDs, and must prove
   those fields survive the actual telemetry sanitizer, not just producer JSON.
2. **Native PDF:** the actual upstream wrapper derives `files[].mimeType` from
   `Blob.type`; the old integration provided no type and expected only legacy
   response spelling. The repair uses the same native binding/endpoint, not a
   global network fallback or an invented free model call. Fresh real conversion
   and normal cleanup/finance are the useful next evidence.
3. **Programmatic Conversation:** the newly executed path duplicated a local
   result through accepted input plus derived publication. It is an actual
   implementation defect, not a reason to repeat the already passing local-client
   and approval journeys. The same continuation also needs child public Response
   identity, not only the stable funded Run identity, for steering capacity.
4. **Automatic compaction:** the root has reported a new actual transport/summary
   failure associated with thinking and a 512-token limit. Retain its original
   operation and known usage; passing standalone compact does not close this new
   path. Its owning repair should supply the exact failure mechanism and one new
   matched path, without replacing this requirement with a narrower smoke test.
5. **Staging capability activation:** MCP's actual count rejection occurred before
   remote/model dispatch. Correct the selector and reviewed Loader tariffs first;
   another paid inference cannot diagnose a disabled capability.
6. **Conversation management latency:** actual normal metadata DELETE took
   22,392 ms and purge 49,151 ms. Phase evidence attributes over 94% of each query
   interval to funding/observation round-trip amplification: actual D1 query
   165–194 ms versus approximately 18 sequential metering calls. The narrow owner
   is batching exact existing metering, not weakening quotas or removing evidence.

The actual original Conversation cleanup is complete, not a blocker: normal
DELETE/purge on `02d483b` settled its original scope to 137 microUSD, released its
output escrow and removed body capacity with zero new Response/model submission.
Its initial HTTP 500 remains a historical failure. See the last section of
[incremental acceptance](incremental-acceptance.md).

## Documentation corrections and final acceptance procedure

The public API document had categorical linear-only, no-hosted-tool and no-remote
attachment statements with no release qualifier; the initial design file called
forks out of scope. Those contradict the expanded objective and current source.
The accompanying documentation-only change marks the original baseline historical,
adds candidate capability links, and explicitly retains production v0.2's Chat
boundary. It does not claim the candidate is already promoted.

Before final completion, update this snapshot from actual owned receipts for the
remaining rows, compose the exact tested Worker/daemon/dashboard/native identities,
and verify the production-preserved historical data without new inference or
container work. Then publish the actual v0.3 native archives/checksums and immutable
tag/release. An older successful artifact, an incomplete aggregate, a planned job
or an empty test filter must not be relabeled as a fresh passing release.

The official [token-counting guide](https://developers.openai.com/api/docs/guides/token-counting)
was retrieved for this audit: count must represent rendered input rather than a
character heuristic. The existing scoped contract inventory remains the broader
API authority; this audit did not reread every upstream page or run old tests.
